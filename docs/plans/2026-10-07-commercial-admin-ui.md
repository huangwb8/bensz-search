# 后台前端商用化优化计划

> 实施状态（2026-10-07）：阶段 0–3 的全部 P0–P2 项已落实，源码开发版本 1.1.0，按发布要求统一交付为 1.0.5。逐项结果及验证边界见[商业后台验收](../smart-search-router/commercial-admin-verification.md)，使用与接口说明见[商业后台说明](../smart-search-router/commercial-admin.md)。以下保留实施前的计划与审计判断。

## 背景与依据

目标：以商用 SaaS 控制台的标准审视 `/admin` 管理员后台和 `/app` 用户工作台，找出界面设计、可用性和工程上的不足，制定分阶段优化路线。本文只是计划，不包含代码修改。

- 审计基线：`404c56994a4fba2dd7b8a6dd74d65c24a52e8d81`，加上工作区里未提交的 1.0.5 品牌区修订。
- 审计对象：[index.html](../../src/bensz_search/static/index.html)、[app.js](../../src/bensz_search/static/app.js)、[styles.css](../../src/bensz_search/static/styles.css)，以及它们调用的 [admin.py](../../src/bensz_search/admin.py)、[admin_store.py](../../src/bensz_search/admin_store.py)、[telemetry.py](../../src/bensz_search/telemetry.py)。
- 方法：
  - 由 awesome-code 门禁派发 frontend-specialist 做只读诊断。
  - 用本机 Chrome 加载正式静态资源，配合合成 API 数据，在 1440×900、1024×768、390×844 三个视口截取 14 个场景，并用 DOM 探针测量对比度、点击区域和焦点。
  - 主代理对照源码复核关键结论。
- 证据边界：
  - 截图基于合成数据，没有连接真实 provider、Docker 或真实部署。
  - 没有在 Safari、Firefox 或屏幕阅读器上测试。
  - 下文标"推断"的结论需要在实施时先复现。
- 既定方向（来自 [2026-10-05-series-ui.md](2026-10-05-series-ui.md)，本计划继续沿用）：
  - 与 bensz-router 同系列的白灰蓝色板、首页衬线标题、浅色侧栏。
  - 管理员区和用户区两组可折叠导航，44px 主控件。
  - 原生 HTML/CSS/JS，零依赖。

## 总体判断

现有界面的视觉基调整洁，已经和 bensz-router 形成系列感，作为"能用的内部工具"是合格的。与商用控制台的差距主要不在配色，而在下面五点：

- **运行可见性不足**
  - 概览只展示请求数和回退数两个累计计数。
  - 后端遥测里已有的数据都没有呈现：按服务和状态拆分的计数、单次延迟、费用估算、路由理由、融合贡献。
  - 服务的健康和熔断状态没有暴露给后台。
  - 管理员无法回答"哪个服务在失败、慢在哪里、钱花在哪里"。
- **存在会改变运行行为的前端缺陷**：启停或编辑 SearXNG 服务时，会清空已验证的引擎证据（见 BUG-1）。
- **关键工作流粗糙**
  - 服务配置对话框太长，不能"保存并测试"。
  - 调试台的执行详情是原始 JSON。
  - 一次性展示的密钥可以被误关。
  - 用户只能新建和删除。
  - 手机上的表格操作列会被挤出屏幕。
- **交互反馈不成熟**
  - 每次操作后整页重新渲染，滚动位置和焦点都丢失。
  - 会话过期时直接跳到登录页，正在填的表单丢失。
  - 错误没有分类，还混着英文原文。
- **工程结构拖慢迭代**
  - `app.js` 由超长字符串模板拼成，最长一行约 4000 字符。
  - `styles.css` 第 62 行单行约 7250 字符。
  - 有 23 个写死的颜色和 18 种字号。
  - 每次改界面都只能往文件末尾追加补丁。

## 设计方向

延续既定的系列视觉，不推翻品牌，只做增量演进。

**主方向：运营级信息密度**

- 去掉内页的英文小标题，页头只保留中文标题、一行说明和主操作，把首屏留给数据。
- 指标卡明确统计口径（如"本进程"、"近 24 小时"），配小趋势线，数字和 ID 用等宽字体。
- 全站统一四种状态徽章（正常、降级、熔断或冷却、停用），颜色和图标同时表达状态，不只靠颜色。

**辅助方向：右侧抽屉 + 执行时间线**

- 服务配置、调用详情、调试结果都在右侧抽屉中展开，保留列表上下文。
- 概览、调试台、服务测试共用一个"路由 → 尝试 → 融合"时间线组件，替代原始 JSON；原始 JSON 收进"高级"折叠区。

**设计变量**

- 颜色：在现有变量基础上补齐 `--warning`、`--info`、`--danger-light`、`--border-strong` 等语义色，输入框边框对比度提高到 ≥ 3:1。
- 字号：收敛为 `12 / 13 / 14 / 16 / 20 / 28` 六档，正文不低于 12px。
- 间距：采用 4px 基数阶梯（4、8、12、16、20、24、32、48）。
- 暗色模式：先完成变量迁移，再整体增加。

## 分阶段实施

每个阶段可以单独交付，单独记录在 CHANGELOG。阶段之间按依赖顺序推进，但阶段 0 可以立即开始。

### 阶段 0：正确性与低成本修复（约 1 天）

- **范围**
  - BUG-1：后端更新服务时保留请求中没有的引擎证据字段，或新增只改启停状态的 `PATCH /providers/{name}`，前端启停改用它。
  - BUG-3：测试查询的 `maxlength` 与后端一致，改为 1000。
  - BUG-4：密钥状态单独显示为"有效／已撤销"。
  - BUG-5："运行模式"卡改为"服务健康"占位，或在后端返回真实模式。
  - FLOW-2：失败类型映射成中文，取值以 `executor.py` 的 `failure_category` 为准。
  - FLOW-4：一次性密钥对话框关闭时要求二次确认。
  - FB-5：停用最后一个启用的服务时给出警告。
  - A11Y-2：提高输入框边框对比度。
- **验收**
  - 新增 pytest：已同步引擎的服务经启停或编辑后，`verified_engines` 不变。
  - `tests/test_admin.py` 等现有用例全部通过。
  - 三个视口截图对比，没有回归。
- **风险**：后端保存语义从"整条覆盖"变成"不传即保留"，需要确认没有调用方依赖"传空即清空"；更稳妥的做法是只对证据字段保留。

### 阶段 1：工程与设计系统地基（约 2–3 天，界面基本不变）

- **范围**
  - ENG-2：拆开 CSS 长行，按"变量 → 基础 → 布局 → 组件 → 页面 → 响应式"分段，合并重复的媒体查询；落实 VS-1、VS-2 的变量。
  - ENG-1：
    - 引入默认转义的 `html` 标签模板函数。
    - 把面板、表格、状态徽章、对话框、空态、确认框抽成函数组件。
    - 统一使用事件委托。
    - 改为原生 ES 模块：多个 `static/*.js`，`index.html` 用 `type="module"` 加载。
    - 不引入构建工具。
  - FB-1：局部刷新，保留滚动位置，加骨架屏。
  - A11Y-1：切页后焦点移到页面标题，保存后焦点回到触发元素。
  - FB-2：提示消息改为队列，错误用 `role="alert"`，可以手动关闭。
  - FB-3：会话过期改为弹出"重新登录"对话框，登录成功后不丢失当前页面状态。
  - IA-1：管理员区的"访问密钥"改名为"我的密钥"，或合并重复入口。
  - VS-3：去掉内页英文小标题。
  - ENG-3：加入稳定的 `data-testid`，并在 `tests/` 新增 UI 冒烟脚本（合成数据，可选执行）。
- **验收**
  - 三个视口逐页截图，与改造前对比，视觉差异只来自预期调整。
  - CSS 中写死的颜色 ≤ 3 个，字号 ≤ 8 种。
  - `app.js` 及拆分后的模块没有超过 300 字符的行。
  - JS 语法检查和现有 pytest 通过。
- **风险**：重构面广。按"一个组件一次提交加截图对比"小步推进，不在同一提交中混入功能变更。

### 阶段 2：运行可见性与调试体验（约 3–4 天，后端少量配合）

- **后端范围**
  - DATA-2／COM-5：管理接口返回各服务的健康状态、熔断状态、冷却剩余时间和最近一次错误分类，只读，不含凭据。
  - DATA-3：遥测事件增加 `timestamp`。
  - DATA-1：`/overview` 在服务端预先聚合各服务的成功率、p50／p95 延迟和估算费用，前端不再自己从原始计数推算。
- **前端范围**
  - 概览：指标卡带口径和趋势，按服务统计的表格，健康徽章。
  - 最近调用：最多显示 20 条，状态中文化，点击行在抽屉中查看时间线。
