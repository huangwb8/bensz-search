# 应用响应与页面切换优化计划

2026-10-07。状态：已按本计划落实 P0–P2；实现与测量见[性能优化实现与验证](../smart-search-router/performance-implementation.md)。依据见[性能诊断](../smart-search-router/performance-diagnosis.md)。本计划保留现有 `1.0.8` 版本，后续变更记录追加至 `[Unreleased]`，发布版本由人类指定。

## 究竟发生了什么

当前页面常常要等后台把数据全部准备好才显示；而后台遇到数据库写入或锁等待时，会连带拖住其他请求。比如从 Search API 切到搜索调试，表单其实只需要可用服务列表，却还要等完整统计返回；返回刚刚访问过的概览，也会再次经历同样的等待。

优化后，已加载的页面应立即出现，变化的数据在后台更新；首次访问时，表单和页面结构先可用，统计模块独立加载。后台即使有一次慢写入，也应让菜单数据、其他搜索和健康检查继续得到响应。这两项改变共同决定“丝滑”的体验。

## 专业判断与优先级

诊断已经通过合成实验复现两项机制：数据库或应用锁竞争会阻塞异步调度线程；界面显示时间随概览接口延迟增长。dudu 的独立查询、30 秒数据新鲜期提供了可借鉴的方式。本项目可以沿用原生 ES 模块和 SQLite，先补齐这些行为。

| 优先级 | 要解决的问题 | 预期用户变化 |
|---|---|---|
| P0 | 同步 store、持久化和锁等待阻塞事件循环 | 一个慢请求不再让整个后台一起停住 |
| P1 | 重复取数、搜索表单等待统计、整页加载互相牵连 | 已访问页面快速返回，首次进入也能先开始操作 |
| P1 | 概览 payload、静态资源缓存策略 | 重新打开和统计刷新更轻，网络较慢时改善更明显 |
| P2 | 实际负载下的容量、长列表和持续运行 | 并发增大、数据积累后仍保持稳定 |

线上故障的具体触发条件仍需现场记录补齐。没有取得 OOM、持续内存增长或真实大列表卡顿证据时，不把它们写成已经确定的原因。

## 要达到的目标

首先建立下面的验收门槛。数值是实施目标，需在固定机器、浏览器、数据和负载条件下验证，不能视为当前已有能力或对任意网络的承诺。

| 指标 | 初始目标 | 测量条件 |
|---|---|---|
| 已缓存页面点击到可操作内容 | p95 ≤ 100 ms | 同一会话、缓存仍新鲜、桌面 Chrome，至少 100 次切换 |
| 首次页面结构和可输入表单出现 | p95 ≤ 150 ms | 本地资源已加载，API 人为延迟 350 ms，至少 100 次 |
| 轻量管理读取 | p95 ≤ 200 ms | 同机 HTTP，8 个并发合成搜索，同时读取概览/服务/健康，至少 500 次 |
| 事件循环调度间隔 | p99 ≤ 50 ms，无 ≥ 200 ms 停顿 | 5 ms 心跳、注入 350 ms SQLite 写锁和应用锁竞争 |
| 统计与密钥计数 | 无重复、无无声丢失 | 并发、取消、故障和优雅退出后与完成事件逐项核对 |
| 快速切换 | 无旧数据覆盖、无持续累积的过期读取 | 每 25 ms 切换一次，重复 20 轮，最后页面正确 |

轻量读取目标要求解除应用层读写互相阻塞后验证；单纯把数据库操作移到线程池，只能保证调度响应，不能保证读取立即完成。缓存命中的内容显示不等待本轮请求结束；需要权限重新确认时，按权限状态展示相应界面。

本次保持搜索 API、鉴权、CSRF、密钥撤销、用户隔离、路由 deadline 与 fallback 语义。现阶段实施围绕已证实的路径展开，容量扩展由后续测量决定。

## P0：消除拖住整个服务的路径

### 修正异步调用与数据库之间的边界

把异步函数中的同步 store 调用移到受控工作线程，重点覆盖 managed API 鉴权、后台搜索、provider 测试/同步，以及 `/ready` 的数据读取。保留已经由 FastAPI 在线程池执行的同步 endpoint，避免无收益地重写整个管理层。

让 `Telemetry` 在短临界区内完成内存计数并形成事件，释放 telemetry 锁后再进行数据库持久化。第一阶段采用可等待的线程卸载：响应仍等待这次记录的结果，但等待期间其他请求可以调度；显式捕获该事件对应的 key/user 归属，跨线程后继续正确记账。原生、auto、planned、MCP 和后台搜索统一遵守这条边界。

避免只将整段 telemetry 放进线程而继续让数据库 I/O 占住 telemetry 锁。线程池容量和排队需要有界；超时或取消等待并不会强行停止已经运行的 SQLite 线程，实施时应跟踪其完成状态，保证计数和错误处理明确。

如果后续测量发现逐次提交仍影响吞吐，再评估有界合批写入。合批方案必须先定义接收、持久化、退出排空与失败告警的行为；不能以无界 `create_task` 或可丢弃队列替代用量记录。

主要涉及 `admin.py`、`admin_store.py`、`telemetry.py`、`router.py`、`integration.py`、协议执行入口和 `server.py`。实施时沿调用链核对所有入口。

### 缩短共享锁，减少读取等待

将登录及改密的 scrypt 运算移出 store 全局锁。运算完成后，在事务内重新检查密码版本、启用状态和用户是否仍存在，避免并发停用、改密或删除造成过期校验通过。

在后台观测中增加锁等待与事务耗时；将 365 天保留清理改为有间隔的维护操作，避免每次搜索重复触发。依据实测再引入少量独立读连接或专门的串行写执行器，让 WAL 的并行读取实际发挥作用；新连接仍需设置 foreign keys、busy timeout，并保留用量合并和跨进程事务保护。

可用服务列表、版本和配置摘要适合由已经发布的配置快照读取，从鉴权和 readiness 热路径移除重复数据库查询。快照应与路由配置代次一起发布，保存、启停和导入后立即失效。密钥、用户状态及 CSRF 的检查仍由服务端强制执行。

对用户而言，这一步让统计写入、登录或一次配置操作不再把其他页面请求拖入长队。

## P1：让切换与完整数据返回分开

### 增加有界的会话内数据缓存

为资源建立内存缓存键：身份代次、用户、角色/工作区、资源名称、时间窗口、筛选和分页参数。服务列表初始采用 30 秒新鲜期；概览和用量初始采用 5–10 秒，并显示更新时间。相同资源的并发读取复用同一个正在进行的请求。

缓存新鲜时立即显示；过期时显示已有数据和刷新状态，同时更新。服务编辑、密钥撤销、用户变更和时间窗口切换按资源定向失效。退出、重新登录以及角色变化时清空对应缓存；数据只保存在当前页面进程中，避免持久化身份数据和跨用户复用。

同一资源被多个页面共享时，以订阅者管理请求：离开页面只取消无人需要的读取，避免一次切换取消其他页面仍需要的数据。搜索提交、配置写入和密钥操作不按导航读取的规则自动取消或重试。

### 分区显示，给搜索表单独立的数据入口

搜索页先渲染表单和保存的草稿；服务选项读取精简配置，完整概览统计独立于搜索页。数据尚未准备好时，只禁用依赖它的选择/提交操作，并给出明确状态。

用户概览的欢迎区、服务/密钥摘要和个人统计分别渲染、分别处理错误，某块失败不会抹掉其余内容。刷新已有页面时保留内容和焦点，使用局部更新状态；继续保留现有草稿、未保存提醒、一次性密钥展示和会话过期后的重新登录。

为页面读取设置独立的短超时，初始 5 秒；搜索、provider 测试和引擎同步继续根据实际 deadline 设置较长上限。页面读取失败后展示可用缓存和重试入口，取消引起的结束不弹出网络错误。所有写入保持明确结果语义，避免盲目重试。

这一阶段的成功表现是：点击菜单立即看到目标内容，搜索页可以先输入，统计随后更新。

## P1：减轻概览与整站重新加载

概览只返回页面所需的统计和最近 20 条摘要；请求详情按 `request_id` 单独读取，继续保留最多 200 条进程历史与原有详情能力。对新旧管理客户端提供兼容默认值；保持已有 `/smart-search/metrics` 和搜索响应契约。

将公共静态文件与私有 API 的缓存策略分开。HTML、会话、身份数据、一次性密钥及私有 API 继续遵循现有保护要求；公共 JS/CSS 使用内容指纹 URL 和长期缓存。指纹须覆盖相对 import 的整个模块图，不能只给 `app.js` 加参数。通过原子发布和浏览器刷新验收，保证旧 HTML 能加载对应资源、新页面不会混用旧模块。压缩由实际服务或反向代理配置决定，先验证响应头与传输大小。

当前五个 JS 模块约 112 KB；可先做缓存和压缩，代码拆分以首屏测量为依据。这一步改善重新打开应用和慢网络体验。

## P2：以实测决定容量与长列表方案

### 保持交互请求在负载下可服务

建立固定 mock provider 延迟的并发阶梯：1、8、16、32，记录搜索完成率、管理 API 延迟、线程/连接/任务数、SQLite 等待和内存。真实 provider 只用外部凭据进行短程确认，单独报告供应商延迟和错误，不混入本地性能结论。

根据结果设置应用层搜索并发上限和有限排队/快速拒绝，为管理与健康请求留出容量。Uvicorn 的 64 门槛只能作为外围保护；还需测试 keep-alive 连接与外部调用扇出的影响。搜索过载应明确返回可重试状态，不能无限排队。

先在单 worker 下完成优化。若以后需要多 worker，先设计跨进程配置代次更新、权限失效和健康/统计一致性，再按实测常驻内存选择数量。当前 1 GiB 配置下直接增加 worker 缺少容量和一致性依据。

### 大数据量时再限制列表工作量

针对实际密钥和用户规模，测量 100、1,000、5,000 行的 API、筛选、排序和 DOM 更新。出现长任务后，为列表增加服务端分页和筛选，建议每页 50 条；输入采用短防抖和局部更新。审计深分页或复合筛选是否需要索引，用实际查询计划与耗时决定。

保留兼容参数或迁移已有调用方。数据库现有使用量索引已经覆盖日期/用户等路径，不以“缺少索引”作为所有查询慢的通用解释。

## 实施顺序与交付范围

1. 建立基线和最小观测：补齐 HTTP 总耗时、事件循环调度、锁/事务等待，固定合成负载与浏览器条件。
2. 完成 P0：解除异步请求上的同步等待和长临界区，验证权限、用量、取消及并发完整性。
3. 完成页面缓存、分区加载和概览精简，验证管理员/用户两套工作区及快速导航。
4. 完成静态缓存与发布一致性；在实际目标容器做容量阶梯与持续运行，按证据选择 P2 改动。

每阶段独立交付和回滚。第一批做到 P0 与页面加载 P1 即可形成直接可感知的改善；P2 由具体测量触发。计划制定时的正式产物为诊断和计划；2026-10-08 已进入实现，代码与验证结果见对应实现文档。

## 如何确认完成

后端验证必须覆盖“慢操作存在时，其他请求仍能运行”。使用真实 ASGI 请求并注入 SQLite 写锁、store 锁和慢 provider，同时访问管理与健康接口；再核对并发搜索的全局/个人用量、密钥次数、撤销/停用即时生效，以及取消和退出时的记录状态。仅检查函数返回正确不足以证明性能改进。

浏览器验证使用同样的延迟注入和固定数据，记录 100 次以上的导航 p50/p95、冷/热缓存请求数、首个可操作内容时间、过期读取取消及页面错误。在 1440、1024、390 三种宽度检查导航、草稿、弹窗、重新登录、焦点和滚动恢复。再测试一个分区 5 秒超时的情形，确认其他分区可用。

部署验证在固定资源预算下同时记录镜像 revision、worker 数、健康响应、RSS/PSS 或容器内存、CPU、线程与连接数、OOM/重启和错误率。建议先进行 30 分钟混合负载，再观察 24 小时真实使用；内存和队列应在相同循环后进入稳定区间，退出后回落到可解释水平。Docker `unhealthy` 需要显式告警和恢复策略，不能假定 restart policy 会处理。

完成标准包括达到前述目标、已有搜索和管理回归通过、无新增越权或计数错误、部署后同样条件可复现改善。真实网络明显影响数据更新时间时，单独报告接口与外部搜索延迟，不把 UI 缓存命中速度当作检索性能。

## 风险与恢复

数据缓存和后台刷新引入时，重点防止角色切换后继续显示旧身份数据、服务配置变更后选择旧 provider，以及后台刷新覆盖正在编辑的表单。服务端权限仍是最终判断依据。

线程卸载和持久化改动重点防止重复计数、丢失计数、超时后事务仍在提交，以及错误关闭共享连接。上线前做 SQLite 一致快照；新表或索引采用增量迁移，保留旧镜像可读的数据格式。

发布时分别验收 P0、页面数据加载和资源缓存。出现记账、鉴权或配置一致性回归时回滚该阶段；出现模块缓存混用时回滚 HTML 与配套静态资源整套产物。保持部署范围仅覆盖搜索服务。

待补齐的现场信息是最易复现的操作、实际部署资源及镜像、卡顿期间日志和浏览器请求瀑布。它们会影响容量与线上最终归因，但不妨碍先修复已经复现的两条路径。
