# 本地产品上线与后台实施计划

## 通俗解释：究竟发生了什么

目前主端口接入演示数据，用户不能登录或配置自己的搜索服务。例如管理员想更换搜索 API 时，只能修改文件；完成后能在后台添加凭据、验证连接并立即用于真实搜索，重启仍保留配置。

## 专业判断：问题在哪里

8898 的 fixture 验证了协议，不能满足产品交付；现有 SearXNG 普通网页引擎部分遭遇 CAPTCHA，200 响应也可能没有结果。必须用实际结果验收，并提供错误诊断。登录、配置持久化、密钥管理和后台界面目前均缺失。

## 要达到什么目标

本机 Docker 主入口运行真实检索，提供中文登录后台、Search API 配置与测试、搜索调试、访问密钥和用户管理。复用 LiteLLM adapters 与原生 POST API；本次用户明确要求后台，覆盖原先 MVP 不做 Web UI 的范围限制。公网域名和远程服务器不属于本次部署。

## 改进方向

### 后台与权限

管理员管理 provider 和用户，成员使用搜索和自己的密钥。密码使用不可逆哈希，登录采用会话和跨站请求保护；provider 凭据加密保存，接口返回脱敏配置。初始管理员凭据随机生成，仅保存在项目忽略的本地配置中。

### 实际生效的搜索配置

后台保存 provider 后更新运行中的 LiteLLM Router 和能力映射，无需手动重启。SQLite 保存配置、用户、会话与访问密钥，Docker 数据卷保留数据。支持已适配的六类 provider、多条同类型配置和每条配置的启停、超时、引擎选择。

### 部署与入口

提供幂等本地初始化命令、非 root 镜像、持久化卷和健康/就绪检查；默认真实配置，不允许生产误用 fixture。浏览器入口指向登录后台；保留原生搜索 POST 兼容性。

## 实施范围与顺序

1. 固定接口约定，前端专项实现与服务端实现并行。
2. 完成用户/会话/密钥/配置持久化和 Router 热更新。
3. 构建本地镜像、切换主端口为真实服务。
4. 验证登录、权限、CSRF、配置增改删、真实搜索、重启持久化和桌面/手机界面。
5. 同步部署文档、变更记录、验证证据和 BAC。

## 如何确认完成

浏览器登录后能添加至少两种 provider 配置并完成连接测试；真实 SearXNG 查询返回实际外部链接，未配商业凭据时报告未验证。新建访问密钥可调用原生 API，撤销后拒绝调用；配置变化立即生效，重启数据保留。自动化测试与静态检查通过，桌面/手机无内容溢出。

## 风险与待确认事项

本次单机、单进程部署，SQLite 用于配置和身份持久化，运行指标与熔断仍是进程内状态。外部搜索引擎会限流或 CAPTCHA，界面必须呈现真实故障；未提供商业 API 凭据时不能声称商业源实测通过。公网 TLS 与多节点部署留待用户另行指定。
